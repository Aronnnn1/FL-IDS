Boosting vs. Deep Learning, and the full FL-IDS pipeline

A federated, cascade-based intrusion detection system for IoT/IIoT traffic — a supervised LightGBM classifier as the first pass, with a client-side autoencoder as a federated, poisoning-resistant backstop for zero-day attacks. This page reports two things: (1) a head-to-head comparison of the boosting classifier against a deep-learning classifier for the same job, and (2) verification that the full five-part pipeline works end to end, with its real limitations stated plainly.

Dataset: Edge-IIoTset (Ferrag et al., 2022). All numbers on this page come from real runs of the code in this repository — see PAPER_NOTES.md for full detail, sources, and every caveat.

Boosting vs. a supervised DL classifier

This answers a specific question: if you swap LightGBM boosting for a deep-learning classifier as the cascade's first pass — same attack-type labels, same task, comparable effort — which one is actually more accurate? Both were trained and evaluated on the exact same 500,000-row sample (400k train / 100k test, stratified), boosting on raw features, the DL classifier on standardized features (each model gets the input representation it needs).

Per-class recall — where the gap actually is

Boosting doesn't win uniformly. The gap concentrates almost entirely on application-layer attacks that look like legitimate traffic; on the trivially-separable flood attacks, both models are essentially perfect.

Why boosting wins here. Gradient-boosted trees build axis-aligned decision splits directly on the engineered flow features (packet counts, flags, protocol fields) — exactly the kind of thresholded, tabular structure this data has. A small dense network has to learn that same decision surface from scratch through weighted sums and nonlinearities, with far less inductive bias toward tabular data, and with 400k rows and 15 epochs it doesn't get there for classes whose boundary with "Normal" is subtle (XSS, SQL_injection, Uploading, DDoS_HTTP — all under 71% recall for the DL model, several under 30%). On the flood attacks (DDoS_TCP/UDP/ICMP), where a couple of features separate the classes almost perfectly, both models hit ~100% — there's no boundary subtlety for either architecture to struggle with.
Honest caveat. This DL classifier was deliberately modest — 2 hidden layers, 8,271 parameters, 15 epochs — a comparable-effort baseline, not an exhaustively tuned one. A larger or longer-trained network might close some of this gap; that wasn't tested. The right claim is "this DL classifier doesn't beat boosting here," not "DL cannot work on this problem."

Confusion matrices

Rows are the true class, columns the predicted class, shaded by the fraction of that row's rows landing in each column (so the diagonal reads as recall). Hover a cell for the exact count.

Boosting

Boosting's confusion is almost entirely inside a small application-layer cluster — DDoS_HTTP, Password, SQL_injection — and a Backdoor/Uploading pair, both semantically related traffic types. It essentially never confuses a flood attack with anything.

DL classifier

The DL classifier's confusion is much more spread out, and dominated by one column: Password absorbs large fractions of DDoS_HTTP, Normal, SQL_injection, Uploading and Vulnerability_scanner — a strong "when unsure, guess Password" bias that boosting doesn't show, and the concrete mechanism behind its much higher benign false-positive rate (real Normal traffic getting pulled toward Password).

Full pipeline — verified working, with real numbers

Beyond the classifier comparison above, this checks that the complete five-part system — boosting cascade, federated autoencoder, poisoning-resistant aggregation, and SDN mitigation — actually works end to end, not just in isolated unit tests.

  • Ablation
    verified    Full cascade beats boosting-alone and autoencoder-alone under 30% poisoned clients: 0.887 / 0.875 / 0.191 attack macro-recall respectively. The autoencoder backstop nearly doubles zero-day detection (0.731 vs. 0.518 for boosting alone) while barely moving known-attack recall — its value is specifically in catching attacks boosting was never trained on.
  • Poisoning resistance
    verified    Attack macro-recall stays in a tight 0.878–0.887 band from 0% to 40% malicious clients. At 50% the trust filter's median-based defense breaks down as expected (malicious survival jumps to 96%) — a known, documented limit, not a surprise failure.
  • Zero-day detection
    verified    All 14 attack classes tested leave-one-out. On classes boosting has zero training signal for, the cascade's detection comes almost entirely from the autoencoder: MITM 0%→89%, DDoS_UDP 9%→90%, Vulnerability_scanner 10%→84%.
  • Real federated training
    verified    A real Flower server plus 10 real separate client processes (not a simulation) completed 20 rounds end to end: 0.889 attack macro-recall, 0.0346 benign FPR — closely matching the faster in-process simulation used for the sweeps above, a useful cross-check that the simulation is representative.
  • Live SDN mitigation
    verified    A real captured attack (Backdoor_attack.pcap) replayed through a live Mininet/OpenFlow topology was classified Backdoor (99.7% confidence) and a real flow rule was installed to block it — confirmed directly against the switch's own flow table, not a mocked result.
  • Live dashboard
    verified    Watched live in a browser during a real training run — round counter, per-client trust scores, reconstruction error, all populated with real, changing data. This check also found and fixed a real bug in the documented launch command that no unit test had caught.

Real limitation, found by this run. The flow table shows 23,586 packets already matched the default "allow" rule before the block rule's own timer starts — meaning classification happens only after the whole capture has been analyzed, not packet-by-packet in real time. For a replayed file, nearly the entire capture passes through before mitigation kicks in. This is an architectural property of the current pipeline (batch classification of a capture), not a bug, and it's stated here rather than glossed over.

Caveats and limitations

Stated plainly, matching the standing convention in this project's own notes: every number above is real, but every result has a scope. Full detail and reasoning for each is in PAPER_NOTES.md.

  1. Mitigation is not real-time. As shown above, Phase B classifies a full capture, not a packet stream — real-time inline blocking is not what's built or measured here.
  2. The DL classifier comparison used a non-default, rebalanced sample. Its absolute benign false-positive numbers (16% boosting, 53% DL) aren't comparable to the pipeline's natural-distribution numbers (0.02% boosting FPR) — the sample deliberately cut the benign class from 71% to ~10% of the data to fix severe class imbalance, which shifts what each model treats as its default prediction. The relative result (boosting beats this DL classifier) is sound regardless.
  3. Non-IID vs. malicious data is a real confound. The trust filter targets corrupted model updates, not unusual local data — an honest client with a very skewed data shard can look similar to a poisoned one, and is sometimes wrongly excluded for a round.
  4. The trust filter has a documented breaking point. At 50% malicious clients, its median-based reference direction becomes the attackers' own direction, and the defense inverts. Trimmed-mean aggregation alone also fails once colluding attackers exceed its trim fraction.
  5. Only one attack model tested — a sign-flip gradient attack with an inflated reported example count. Adaptive attackers designed specifically to evade this filter are untested.
  6. Mostly single-seed results. A targeted multi-seed check on one flagged anomaly (a 20%-vs-30% ordering in the poisoning sweep) found it does not hold across seeds — confirmed as noise, not a real trend, and documented as such rather than silently repeated. Most other numbers on this page are still single-seed.
  7. Tiny classes. MITM (358–406 rows) and Fingerprinting (853 rows) are a small fraction of the full dataset; their per-class numbers rest on few test rows and should be read with that in mind.
  8. Novelty is not a settled claim. A handful of targeted literature searches found no single published system combining all five components here — that is not a systematic review.
