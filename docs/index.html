Boosting vs. Deep Learning, and the full FL-IDS pipeline

A federated, cascade-based intrusion detection system for IoT/IIoT traffic: a supervised LightGBM classifier as the first pass, with a client-side autoencoder as a federated, poisoning-resistant backstop for zero-day attacks. This site reports (1) a head-to-head comparison of boosting against a deep-learning classifier, (2) how long things take and why, (3) concrete ideas for pushing macro F1 past 0.95, (4) a visual and step-by-step explanation of the whole pipeline, and (5) verification that it works end to end, with its limitations stated plainly. Every table of numbers is collected on the cumulative results page.

Dataset: Edge-IIoTset (Ferrag et al., 2022). All numbers come from real runs of the code in this repository. Full notes and sources: PAPER_NOTES.md.

Boosting vs. a supervised DL classifier

If you swap LightGBM boosting for a deep-learning classifier as the cascade's first pass — same attack-type labels, same task, comparable effort — which is more accurate? Both were trained and evaluated on the exact same 500,000-row sample (400k train / 100k test, stratified); boosting on raw features, the DL classifier on standardized features (each model gets the input representation it needs).

Boosting (LightGBM)DL classifier (dense MLP, 8,271 params)

Per-class recall — where the gap actually is

Boosting doesn't win uniformly. The gap concentrates on application-layer attacks that look like legitimate traffic; on the flood attacks both models are essentially perfect.

Why boosting wins here. Gradient-boosted trees build axis-aligned decision splits directly on the engineered flow features (packet counts, flags, protocol fields) — exactly the thresholded, tabular structure this data has. A small dense network has to learn the same decision surface through weighted sums and nonlinearities, with far less inductive bias toward tabular data, and with 400k rows and 15 epochs it doesn't get there for classes whose boundary with “Normal” is subtle (XSS, SQL_injection, Uploading, DDoS_HTTP). On the flood attacks, where a couple of features separate the classes almost perfectly, both models hit ~100%.
Honest caveat. This DL classifier was deliberately modest — 2 hidden layers, 8,271 parameters, 15 epochs — a comparable-effort baseline, not an exhaustively tuned one. A larger or longer-trained network might close some of the gap; that wasn't tested. The right claim is “this DL classifier doesn't beat boosting here,” not “DL cannot work on this problem.”

Boosting

Boosting's errors sit mostly inside one application-layer cluster — DDoS_HTTP, Password, SQL_injection, Uploading, XSS and Normal — which together account for … of all its mistakes. Flood attacks (DDoS_TCP/UDP/ICMP) are almost never confused with anything.

DL classifier

The DL classifier's confusion is much more spread out and dominated by one column: Password absorbs large fractions of DDoS_HTTP, Normal, SQL_injection, Uploading and Vulnerability_scanner — a strong “when unsure, guess Password” bias boosting doesn't show, and the concrete mechanism behind its much higher benign false-positive rate (real Normal traffic pulled toward Password). The same cluster holds … of its mistakes, but it also fails on Port_Scanning ↔ DDoS_TCP and Fingerprinting, which boosting handles.

Training time — how long, and why

Short answer: training either classifier is quick (boosting ~1 minute, DL ~10 seconds). What is slow is the evaluation methodology — the poisoning sweep and zero-day experiments retrain the whole federated pipeline 75 and 14 times — and within each of those runs, one component dominates.

Why a full federated run takes ~4 minutes when a round takes seconds

  • Boosting updates are the bottleneck. In the sweep logs a normal round takes ~5–7 s, but a round that includes a boosting update takes ~43 s: clients spend ~10 s filtering their traffic through a now-larger model, then the server spends ~33 s continuing LightGBM training (+50 trees × 15 classes) on the calibration set plus alerts. With an update every 3 rounds there are 6 per run, which by the log timestamps accounts for roughly three-quarters of a run's time (an estimate, not a profiler measurement).
  • Deterministic, single-threaded LightGBM, on purpose. Multi-threaded histogram building is not bit-reproducible: with identical inputs and seed one class's recall swung between 0.0 and 0.88 across runs (PAPER_NOTES §6). The code forces deterministic=True, force_row_wise and num_threads=1, trading speed on a 4-vCPU VM for reproducible science.
  • The model grows during training. Each update adds 50 trees per class (300 → 600 trees over a run), so every later round's client-side filtering and every later update is slower than the last.
  • The evaluation multiplies everything. Every sweep point, ablation variant and held-out class is a complete retraining from scratch (75 + 14 + the 5-variant ablation), so minutes per run become hours.
  • CPU-only, virtualised, memory-constrained hardware. No GPU (irrelevant here — the networks are tiny), 4 vCPUs, and a real multi-process run is memory-bound: 11 Python processes each importing PyTorch/LightGBM nearly exhausted the VM until thread pools were capped.
  • Data loading is paid on every script start. Parsing and cleaning the 1.16 GB CSV takes 15–25 s each time.
How to speed it up (none applied yet): cache the cleaned matrix as Parquet/NPZ instead of re-parsing the CSV; update boosting every 6 rounds or add fewer trees per update; allow multi-threaded LightGBM for exploratory runs (keeping the deterministic setting for reported numbers); and run evaluation sweeps on a machine with enough RAM to run two in parallel.

How to push macro F1 past 0.95

Current boosting macro F1 on the 100k test rows is 0.887. Everything below is a hypothesis grounded in the confusion matrix and per-class numbers above — none of it has been run, and no gain is promised. They are ordered by how directly the evidence supports them.

The F1 budget: where the missing points are

Macro F1 is the plain average of 15 per-class F1 scores, so reaching 0.95 needs the per-class F1 sum to rise from … to 14.25 — a gain of … F1 points spread over the weak classes. Bars show each class's current F1; the red part is its shortfall to 0.95.

strongest evidence1. Move from per-packet to behaviour features

Why: the dataset rows are individual packets, and the pipeline treats each as independent. But the confused classes (DDoS_HTTP, Password brute-forcing, SQL_injection, Uploading, XSS) differ from normal HTTP mostly in behaviour over time — request rate, repeated login URIs, burst structure — not in any single packet's header fields.

What to change: add windowed features per source host (packets/s, distinct URIs, mean inter-arrival time, method mix, response-code mix) and join them back onto each packet. frame.time and ip.src_host exist in the CSV but are dropped at load by the authors' recipe, so this is possible.

Risk: Phase B must compute identical windows from a live capture; windows must not straddle the train/test split.

strong evidence2. Restore content signals the recipe drops — as numbers, not text

Why: SQL injection, XSS and file upload differ from normal HTTP in what is sent, and the authors' recipe drops exactly those columns (http.request.uri.query, http.request.full_uri, http.file_data, tcp.payload) because they are high-cardinality text.

What to change: keep the text out but derive scalars: URI/query/payload length, byte entropy, counts of special characters (' % ; < > --), keyword flags (select, union, script), multipart/upload markers.

Risk: this dataset already had a label leak from an export artifact, so every new feature must pass the existing single-feature AUROC guard (< 0.9) before it is trusted.

cheap3. Per-class decision thresholds instead of plain argmax

Why: the per-class table shows clear precision/recall asymmetry: DDoS_HTTP is over-predicted (precision 0.654, recall 0.914), while Uploading (precision 0.961, recall 0.630) and Fingerprinting (0.832 / 0.579) are under-predicted.

What to change: on a held-out validation split, fit one multiplicative weight per class on the predicted probabilities (or per-class thresholds) to maximise macro F1, then freeze them. Post-hoc, no retraining.

Risk: must be tuned on validation data, never on the test rows, or the 0.95 is fitted to the test set.

targeted4. A specialist second-level model for the confusable cluster

Why: a single 15-way softmax spreads its trees across all classes, but … of boosting's errors are inside one six-class cluster (see the matrix).

What to change: stage 1 routes a packet to “flood/scan/other” or “Normal + HTTP family”; stage 2 is a separate LightGBM trained only on Normal, DDoS_HTTP, Password, SQL_injection, Uploading and XSS, with its own tuning and the new features from items 1–2.

Risk: a stage-1 mistake can't be recovered; evaluate end to end, not stage by stage.

medium5. Tune hyperparameters for macro F1, with early stopping

Why: the booster is fixed at 300 rounds, learning rate 0.05, 31 leaves, with no validation set, no early stopping, no row/column subsampling and default min_data_in_leaf. Those values were picked by held-out log-loss (0.041 vs 0.056 for 127 leaves / lr 0.1), not by macro F1.

What to change: random/Bayesian search over num_leaves (31–255), min_data_in_leaf, feature_fraction and bagging_fraction (0.6–0.9), lambda_l1/l2, max_bin, min_gain_to_split, up to ~2,000 rounds with early stopping on macro F1. Keep min_sum_hessian_in_leaf and lambda_l2: without leaf regularisation this data made training diverge.

medium6. Other boosters, or an ensemble

Boosting is trained on the server, so any library can slot in; nothing in the federation depends on LightGBM.

OptionWhy it might helpCost / caveat
XGBoostDifferent tree growth (level-wise) makes different errors than LightGBM's leaf-wiseSlower on CPU for 15 classes
CatBoostOrdered boosting and symmetric trees are strong on small classes (Fingerprinting, MITM)Slowest to train; model format differs

medium7. More labelled data for the boosting stage, or class weights

In the real pipeline boosting trains on only the 5% server-held calibration set (≈ 76k rows), a deliberate privacy design choice; this comparison gave it 400k. A larger calibration set, or sample weights for the rare classes (Fingerprinting has 853 rows in the whole dataset), may help. Fingerprinting alone costs about 0.018 macro F1 at its current score.

Trade-off: a bigger server-held labelled set weakens the “labels never leave clients” story.

validate first8. Check the target is real before chasing it

Train and test rows are a random split of individual packets, so near-identical packets from the same capture session land on both sides — that flatters every number here. Add a split that holds out whole capture sessions and re-measure the baseline: it will likely read lower than 0.887, and a gain from the ideas above only counts if it survives that split.

Also look at the confidently-wrong rows (e.g. 716 Normal packets predicted Password). If the testbed's “Normal” HTTP and the attack HTTP genuinely overlap at packet level, the ceiling at 0.95 may not be reachable without items 1–2.

Assumptions behind the current number

  • Each row is an independent packet (no temporal context).
  • A random row split is representative of unseen traffic (it likely is not — see item 8).
  • The class-capped 500k sample is a fair test distribution (it cuts Normal from 71% to ~10%, so precision for attack classes is better than it would be on natural traffic).
  • Single seed (42). Seed-to-seed spread was not measured for this comparison.
  • Plain argmax decides the class, with no per-class thresholds.

The pipeline at a glance

Two phases, kept deliberately separate: Phase A trains the models offline (federated), and Phase B loads the saved bundle and enforces decisions on live traffic.

Phase A — data to trained bundle

Data Boosting (supervised) Federated clients / autoencoder Server-side robustness Network / SDN Output artefact

Phase B — traffic to enforcement

The cascade decision rule (one implementation, used by evaluation, dashboard and SDN)

  1. Boosting predicts a class and its probability.
  2. If the class is a known attack and probability ≥ 0.7 → final label is that attack type. The autoencoder is not consulted.
  3. Otherwise (predicted Normal, or an attack without enough confidence) the row goes to the autoencoder: reconstruction error > the client's threshold → “anomalous” (a zero-day signal), confidence = min(1, error/threshold − 1); else benign.

What each stage does, how it works, and the parameters that control it. Values are the ones used in this project's runs (configs/config.yaml); module paths are relative to fl_ids/.

1Load, clean and encode the datadata/pipeline.py · data/repair.py

Function

Turn the authors' CSV into a clean numeric matrix X (1,909,719 rows × 91 features) and integer labels y (15 classes).

How it works

  • Read 47 of 63 columns: 15 ID/timestamp/payload columns are dropped per the dataset authors' own recipe, plus Attack_label (derivable from the target, so keeping it would leak the answer).
  • Canonicalise the placeholder. “Field doesn't apply” is written 0 in some captures and 0.0 in others, and the spelling follows the label — so mqtt.topic_0.0 alone separated benign from attack at AUROC 1.0. Both spellings become 0; the strongest single feature is now ~0.71.
  • Drop NaN and duplicate rows (309,497 duplicates).
  • Repair MITM. The authors' MITM CSV has values under the wrong column names; its 1,214 rows are replaced by 1,229 rows re-extracted from their own pcap with tshark.
  • One-hot encode 7 categorical columns → 91 features.

3Non-IID partition and per-client normalisationdata/pipeline.py

Function

Simulate realistic clients whose traffic differs wildly from each other, and prepare each client's private train/validation/test data.

How it works

  • For each class, draw per-client proportions from a Dirichlet(α) distribution — small α gives strongly skewed clients (one may be 94% benign).
  • Each client splits its rows: 15% test, 15% of the benign remainder as a benign validation slice (to calibrate its anomaly threshold), the rest train.
  • Each client z-scores its features with a scaler fit only on its own training rows (never globally — a global scaler leaks cross-client statistics), clipped to ±10 so a counter-like feature with tiny local variance can't swamp the reconstruction error.
  • A raw (un-normalised) copy is kept for the boosting model, which must always see raw features: a per-client scaler can shift a feature by orders of magnitude and break shared tree thresholds.

data.dirichlet_alpha0.3skew; lower = more non-IID
data.test_fraction / val_benign_fraction0.15 / 0.15per-client held-out slices
data.normalized_clip10.0z-score clip

Observed consequence: client 5 receives no benign validation rows, so its threshold is infinite and its autoencoder never flags anything — reported, not hidden.

5Client round: boosting filter, then autoencoder trainingfl/client.py · models/autoencoder.py

Function

Each client trains an unsupervised autoencoder on its own “normal-looking” traffic, so it can later flag traffic unlike anything benign — the zero-day backstop.

How it works

  • The client runs the broadcast boosting model on its local rows and discards the ones boosting confidently calls an attack (probability ≥ 0.7). The autoencoder trains only on what is left, so it never learns attacks as “normal.”
  • Dense autoencoder 91 → 32 → 16 → 8 → 16 → 32 → 91 (7,299 parameters), MSE reconstruction loss.
  • The client returns updated weights, a 50-bin histogram of reconstruction errors, and (every 3rd round) up to 50 flagged rows with analyst-confirmed labels. Raw traffic otherwise never leaves the client.
  • Anomaly threshold = 97th percentile of reconstruction error on the client's benign validation slice, recomputed every round — so about 3% of benign traffic is flagged by construction.

6Server aggregation: trust filter + trimmed meanrobustness/ · fl/strategy.py

Function

Combine client updates into a new global autoencoder while screening out poisoned (Byzantine) updates.

How it works

  • Work on deltas (new − old weights), never raw weights — raw weights are dominated by the shared global model, so every pair looks ~0.99 similar.
  • Reference direction = coordinate-wise median of the round's deltas; per client compute cosine similarity to it and the L2 norm.
  • Exclude a client if (a) its similarity is a per-round MAD outlier, (b) its update points away from the consensus (cosine < 0), or (c) its running trust score has fallen below 0.5.
  • Norm-clip survivors to 2× the median norm, aggregate with a trimmed mean, and add the result to the round's starting weights. If nobody survives, the round is skipped.
ParameterValueEffect
robustness.mad_outlier_threshold3.0relative, per-round outlier band
min_cosine_similarity / min_trust_score0.0 / 0.5sign check and history gate
trust_ema_alpha0.330% new round, 70% history
norm_clip_multiplier / trim_fraction2.0 / 0.15bound large updates; trim 15% per side

Known limits: at 50% attackers the median becomes the attackers' direction and the filter inverts; late-round attackers look like honest noise.

7Incremental boosting updatemodels/boosting_update.py

Function

Let the supervised model learn from what the autoencoders catch, without clients sharing raw traffic.

How it works

Every 3 rounds, clients that survived the trust filter surface up to 50 autoencoder-flagged rows with the label an analyst would confirm (false alarms come back as “Normal”). The server continues LightGBM training for 50 more trees on the calibration set plus the accumulated alerts. If an alert contains a class the model has never seen, it retrains from scratch — continued training can't learn a new class, because that class's softmax hessian is ~0 and the leaf-regularisation setting blocks every split. The new model is broadcast with the next round.

9Replay and feature extraction (Phase B)sdn/topology.py · sdn/feature_extraction.py

Function

Turn a real captured attack into the same 91-feature rows the models were trained on.

How it works

Mininet builds 10 hosts on one Open vSwitch switch pointed at an os-ken OpenFlow 1.3 controller; host h(i+1) is FL client i. tcpreplay replays the real .pcap from a host while tshark extracts 46 fields per packet, mapped to the authors' spelling (tshark 4.x prints booleans as True/False and shortens hex, which silently zeroed tcp.flags.ack before it was fixed). Rows are one-hot encoded with the training vocabulary and scored with that client's scaler and threshold. Mininet needs root, granted by one narrow sudoers rule for the argument-less topology script.

10Verdict, mitigation bridge and flow rulesdn/live_inference.py · sdn/bridge.py · sdn/controller.py

Function

Reduce thousands of per-packet cascade outputs to one decision per device and turn it into a real flow-table change.

How it works

The device verdict is the most frequent non-benign label across its packets (mean confidence of those packets, and the cascade stage that made most of the calls), or “benign” if none. It is posted to a small REST bridge, which asks the controller to install a rule: a high-priority drop on the source IP, or an OpenFlow meter for rate-limiting. The result is verified against the switch's own ovs-ofctl dump-flows, not the bridge's say-so.

11Evaluation harness and live dashboardeval/ · dashboard/

Function

Measure what each part contributes, and watch a run as it happens.

How it works

  • Variants (same data, same seed): full pipeline, plain FedAvg, trimmed-mean-only (no cosine filter), autoencoder-only, boosting-only.
  • Headline metrics are not accuracy — ~71% of traffic is benign, so accuracy rises when a broken autoencoder stops flagging anything. Use attack macro-recall, benign FPR, detection F1, zero-day macro-recall.

Caveats and limitations

Every number above is real, but every result has a scope. Full reasoning for each is in PAPER_NOTES.md.

  1. Mitigation is not real-time. Phase B classifies a full capture, not a packet stream.
  2. The DL comparison used a non-default, rebalanced sample. Its benign false-positive rates (16% boosting, 53% DL) aren't comparable to the pipeline's natural-distribution numbers (0.02% boosting FPR): the sample cut the benign class from 71% to ~10%. The relative result is sound regardless.
  3. Macro-F1 figures from different experiments are not interchangeable. Boosting scores 0.887 on the balanced 500k test and 0.910 on the natural-distribution test slices of the federated run, where MITM and Fingerprinting have only 1 and 3 test rows. The 0.887 is the more trustworthy figure.
  4. Random-split optimism. Rows are split at random, so near-duplicate packets from one capture session appear in both train and test. A session-held-out split has not been run; all accuracy-type numbers here are probably optimistic.
  5. The improvement ideas are untested hypotheses. No claim is made that any of them reaches 0.95, or that 0.95 is attainable at packet level.
  6. Non-IID vs. malicious data is a real confound. The trust filter targets corrupted updates; an honest client with a very skewed shard can look like a poisoned one and is sometimes excluded for a round.
  7. The trust filter has a documented breaking point. At 50% malicious clients its median reference becomes the attackers' direction. Trimmed-mean alone also fails once colluding attackers exceed its trim fraction.
  8. Only one attack model tested — sign-flip with an inflated example count. Adaptive attackers are untested.
  9. Mostly single-seed results. A multi-seed check on one flagged anomaly (20% vs. 30% in the sweep) showed it does not hold across seeds — noise, not a trend. Most other numbers are still single-seed.
  10. Tiny classes. MITM (358–406 rows) and Fingerprinting (853 rows) rest on few test rows.
  11. Novelty is not a settled claim. A few targeted searches found no published system combining all five parts; that is not a systematic review.
